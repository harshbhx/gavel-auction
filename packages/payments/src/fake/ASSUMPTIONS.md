# Fake PayPal: assumptions register

The fake (`core.ts`, `server.ts`, `faults.ts`, `idempotency.ts`, `webhooks.ts`) stands in for the PayPal sandbox in unit and scenario tests. Everything below is what the fake assumes about PayPal without having observed it in our sandbox (SPEC R-PAY-124). Each row names the gate that will confirm or correct it, where the assumption lives in code, and what the client does if the assumption turns out wrong.

When a gate has run, update the row: set Status to `confirmed` or `corrected`, link the evidence file, and change the fake in the same pull request if it was wrong.

Gates: G1 partial capture, remainder and explicit void (PAY-59). G2 SDK v6 approval page (PAY-60). G3 reauthorize probe and timed honor checks (PAY-61). G4 real webhooks and verification (PAY-62). M measurement run (PAY-64). IDEM sandbox idempotency probe (PAY-68).

| A05 | Capture on a voided authorization fails with 422 `AUTHORIZATION_VOIDED`.                                                                                               | `core.ts` `capture()`                                        | G1   | Same as A04.                                                                                                      | unverified |
| A06 | A voided authorization voided again fails with 422 `AUTHORIZATION_ALREADY_VOIDED` (name assumed).                                                                      | `core.ts` `void()`                                           | G1   | Saga counts `already_voided`, `expired` and `not_found` as released; an unknown 422 name goes to a truth check.   | unverified |

| A09 | Honor period is 3 days (`honorMs`); a capture after it still succeeds unless `afterHonorCapture` is `fail`.                                                            | `core.ts` options `honorMs`, `afterHonorCapture`             | G3   | Hold max age stays far inside the honor period, so the default path never reaches it; reauthorize is conditional. | unverified |
| A10 | Reauthorize inside the honor period fails with 422 `REAUTHORIZATION_TOO_EARLY` (name assumed).                                                                         | `core.ts` `reauthorize()`                                    | G3   | Reauthorize is disabled by default (R-PAY-071); the probe result sets the rule.                                   | unverified |
| A11 | Reauthorize after the honor period replaces the hold amount and restarts the honor clock, up to the capture limit.                                                     | `core.ts` `reauthorize()`                                    | G3   | Same as A10.                                                                                                      | unverified |
| A12 | A payment is declined with 422 `INSTRUMENT_DECLINED` (the fault `capture_declined`).                                                                                   | `faults.ts` `capture_declined`, `core.ts` `capture_declined` | G1   | Classifier maps any other 422 to `rejected`, also definite.                                                       | unverified |
| A13 | Authorizing an order that the buyer has not approved fails with 422 `ORDER_NOT_APPROVED`; authorizing twice fails with 422 `ORDER_ALREADY_AUTHORIZED` (names assumed). | `core.ts` `authorizeOrder()`                                 | G2   | The saga reads the order before authorizing; a different name is still a definite 422.                            | unverified |
| A14 | Creating an order with a non-positive amount fails with 400 `INVALID_AMOUNT` (name assumed).                                                                           | `core.ts` `createOrder()`                                    | G1   | The ceiling is validated before any call (R-PAY-033).                                                             | unverified |
| A15 | Authorization, order and capture ids are sequential (`AUTH-1`, `ORDER-1`, `CAP-1`). Real ids are opaque.                                                               | `core.ts` `nextId()`                                         | none | Not a PayPal behaviour; the client treats ids as opaque strings.                                                  | by design  |

## Idempotency

| ID  | Assumption                                                                                                                      | Code                                  | Gate | Fallback if wrong                                                                                              | Status     |
| --- | ------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------- | ---- | -------------------------------------------------------------------------------------------------------------- | ---------- |
| I01 | The same `PayPal-Request-Id` on the same operation and target with equal parameters replays the stored result.                  | `core.ts` `run()`, `idempotency.ts`   | IDEM | The saga never relies on replay for correctness (R-PAY-050); the truth check decides.                          | unverified |
| I02 | The same request id with different parameters fails with 422 `DUPLICATE_REQUEST_ID_DIFFERENT_PARAMS` (name assumed).            | `core.ts` `run()`, `idempotency.ts`   | IDEM | Client maps only the kind `idempotency_conflict` where the name matches; otherwise a plain 422 `rejected`.     | unverified |
| I03 | Request ids are remembered forever. The fault `forget_idempotency` simulates expiry; PayPal's real retention window is unknown. | `idempotency.ts`, `faults.ts`         | IDEM | Same as I01.                                                                                                   | unverified |
| I04 | Request ids of up to 64 characters are accepted (ours are 44).                                                                  | `server.ts` does not check the length | IDEM | Shorten the id construction (SPEC 4.4).                                                                        | unverified |
| I05 | Idempotency is keyed per `(operation, target id, request id)`, not globally.                                                    | `core.ts` `run()` key                 | IDEM | Request ids are unique per `(auction, op, hold, amount, generation)` anyway, so a global key behaves the same. | unverified |
| I06 | A call refused with a 4xx is not stored: a retry with the same request id executes again and is refused again.                  | `core.ts` `run()`                     | IDEM | The saga re-reads the truth after a refusal; a retry that succeeds later is observed, not assumed.             | unverified |

## HTTP surface of the fake server

| ID  | Assumption                                                                                                                                                                   | Code                                       | Gate  | Fallback if wrong                                                                               | Status     |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------ | ----- | ----------------------------------------------------------------------------------------------- | ---------- |
| H01 | Response bodies follow PayPal's documented field names (`purchase_units`, `payments.authorizations`, `links` with `rel: approve`).                                           | `server.ts` route handlers                 | G1    | Fix the fake and the gateway adapter together; gate evidence holds the real shape.              | unverified |
| H02 | `GET authorization` returns id, status and amount but no list of captures; captures are read from the order (`payments.captures`).                                           | `server.ts` `getAuthorization`, `getOrder` | G1    | Truth check reads whichever place carries the captures; `captures: null` is allowed (SPEC 5.1). | unverified |
| H03 | Void answers 204 with an empty body.                                                                                                                                         | `server.ts` `voidAuth`                     | G1    | Gateway treats any 2xx as success.                                                              | unverified |
| H04 | Capture answers 201 and echoes `invoice_id` and `final_capture`; `final_capture` defaults to false when absent.                                                              | `server.ts` `capture`                      | G1    | Client always sends both fields (R-PAY-051).                                                    | unverified |
| H05 | A capture request without an amount captures the remaining authorized amount.                                                                                                | `server.ts` `capture`                      | G1    | Client always sends an amount.                                                                  | unverified |
| H06 | Orders are created with status `CREATED`, move to `APPROVED` when the buyer approves and to `COMPLETED` once authorized.                                                     | `core.ts` order status                     | G2    | Truth check keys on the authorization, not on the order status.                                 | unverified |
| H07 | Error bodies carry `name`, `message` and `details[0].issue`; the HTTP status maps to the name (404 `RESOURCE_NOT_FOUND`, 422 `UNPROCESSABLE_ENTITY`, 400 `INVALID_REQUEST`). | `server.ts` `errorResponse`                | G1    | Classifier decides by HTTP status class when names differ.                                      | unverified |
| H08 | Every response, success or error, carries a `PayPal-Debug-Id` header.                                                                                                        | `server.ts` `write`                        | G1    | Logging omits the id when absent.                                                               | unverified |
| H09 | The token endpoint answers `expires_in` 32400 and tokens stop working at expiry; a business call with a bad token gets 401 `AUTHENTICATION_FAILURE`.                         | `server.ts` `issueToken`, `checkBearer`    | G0, M | Client refreshes on 401 once and caches for `expires_in` minus 60 s (R-PAY-010).                | unverified |
| H10 | After a 401 from the fault `http_401_once` the presented token is revoked; a freshly issued token works.                                                                     | `server.ts` `dispatch`                     | M     | Client replays once with a new token; a second 401 is `auth_failed`.                            | unverified |
| H11 | Rate limiting answers 429 with `Retry-After` in seconds. The fake never rate-limits on its own, only through the fault `http_429`.                                           | `faults.ts` `http_429`                     | M     | Transport honors a numeric or HTTP-date `Retry-After`, bounded by 30 s.                         | unverified |
| H12 | Latency is zero except through the fault `slow(ms)`. Real latency and its percentiles come from the measurement run.                                                         | `faults.ts` `slow`                         | M     | SPEC R-PAY-152 targets are replaced by measured numbers (PAY-65).                               | unverified |
| H13 | A dropped connection after a successful POST leaves the effect applied (`timeout_after_success`); before processing it does not (`timeout_before`).                          | `faults.ts`                                | M     | The saga treats every network error on a POST as an unknown outcome and reads the truth.        | by design  |
| H14 | A truncated 200 body is possible (`malformed_body`); the call is applied.                                                                                                    | `faults.ts` `malformed_body`               | M     | Client treats an unparseable 2xx body as an unknown outcome.                                    | by design  |

## Webhooks

| ID  | Assumption                                                                                                                                                               | Code                               | Gate | Fallback if wrong                                                                       | Status     |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------- | ---- | --------------------------------------------------------------------------------------- | ---------- |
| W01 | Event types are `CHECKOUT.ORDER.APPROVED`, `PAYMENT.AUTHORIZATION.CREATED`, `PAYMENT.AUTHORIZATION.VOIDED`, `PAYMENT.CAPTURE.COMPLETED`. Resource bodies are simplified. | `core.ts` `emit()`                 | G4   | Handler ignores unknown types and fields; reconciliation reads the truth.               | unverified |
| W02 | Signatures use an HMAC-SHA256 scheme with a fixed test key. | W03 | The verify endpoint receives the original event text spliced into the request body, and answers `verification_status` `SUCCESS` or `FAILURE`.                            | `webhooks.ts` `buildVerifyRequest` | G4   | Handler fails closed: anything other than `SUCCESS` is rejected (R-PAY-091).            | unverified |
| W04 | Events can arrive duplicated, reordered or not at all; the fake's delivery modes (`fifo`, `reverse`, `shuffle`, duplicate, drop) model that.                             | `webhooks.ts` `planDeliveries`     | G4   | Handler is idempotent on the event id and polling reconciliation covers missing events. | by design  |
| W05 | Expiry of an authorization emits `PAYMENT.AUTHORIZATION.VOIDED` with reason `expired`.                                                                                   | `core.ts` `refresh()`              | G3   | Reconciliation reads the authorization status, not the event.                           | unverified |

## Conformance test per unverified assumption

The gateway conformance suite (`test/conformance/suite.ts`, run by `test/conformance/run.test.ts`) runs the same assertions against the fake core, the fake over HTTP and, when the sandbox variables are set (`PAYPAL_ENV=sandbox`, `CONFORMANCE_MANUAL=1`, credentials and `CONFORMANCE_AUTH_IDS`), against the PayPal sandbox. Where the sandbox disagrees with the fake the run records a difference below instead of failing. A row stays `unverified` until a sandbox run has passed its test id; the fake passing it proves only that the fake behaves as written.

| Assumption | Test id                       | Covered by                                                                                                        |
| ---------- | ----------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| A01        | C02                           | Final capture closes the hold; remainder release is observed through the hold status.                             |
| A02        | C11                           | Void of a partially captured authorization keeps the captured amount.                                             |
| A03        | C10                           | A capture far above the limit is refused definitely. The exact 115% / $75 limit has no test: the id needs G1.     |
