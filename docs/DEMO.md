# Demo and judge test guide

How to run the hosted GAVEL demo and check that it does what it claims. Everything runs in the PayPal sandbox only. No real money moves and no real card or PayPal account is needed.

Status labels used below: "available" means the code is on main today. "not available yet" means the part is specified (see `docs/specs`) but not built or not deployed, so the step cannot be followed end to end yet.
`packages/server` has an entry point (`npm start -w @gavel/server`, `src/main.ts`), the auction HTTP routes under `src/http` and a WebSocket gateway (`createGateway`, mounted in `src/boot/compose.ts`). The `/audio` voice socket is mounted in the same file (`createAudioHost`). The scripted `/api/demo/*` routes (`src/http/demo.ts`) are mounted only with `DEMO_MODE=1` and `PAYMENTS=fake`, which config refuses under production-like settings, so no hosted server serves them. The web app is hosted at https://gavel.dualmindlab.tech and the API at https://api.gavel.dualmindlab.tech, both in sandbox mode, with the API on a persistent disk. A recorded end-to-end check of sections 2, 3, 5 and 7 against that host is the next step, so they describe the intended flow; the local fake-payments demo is the runnable path. What runs today is the engine, the settlement code against the fake PayPal and, in nightly specs, on the real sandbox, and the web components, each in its own tests.

This guide is updated as those parts land.

## Two-minute path

Pick the line that fits you. A recorded walk of these steps against the hosted site is the next step; they describe what the code does.

1. No setup, no login: open https://gavel.dualmindlab.tech/demo/scripted, a recorded room that plays in your browser with no server and no PayPal calls. Locally (development build): `npm ci`, then `cp packages/web/.env.example packages/web/.env.local` (the web app needs those `VITE_*` values), then `npm run dev -w @gavel/web`, then open `/r/demo/screen?scripted=1`. The flag plays a recorded scenario in the browser with no server and no PayPal calls; the provenance tag says Scripted. Also try `/r/demo/bid?scripted=1&at=3000` (bidder room in the middle of the scenario), `/r/demo/console?scripted=1&at=5000` and `/r/demo/receipt?scripted=1`; `scenario=<name>` picks another script (for example `outbid_race`, `soft_close` or `kill_switch`; the list is in `packages/web/src/testing/scenarios`). Only development builds honour `scripted=1`; a production build, including the hosted site, ignores it. On the hosted site open `/demo/scripted` instead (the `/try` tour link and the landing "Run scripted demo instead" button go there): this in-app route plays the recorded scenario in the tab in every build, with no server and no PayPal calls, and does not turn `scripted=1` on.
2. Key-less sandbox room (hosted, only when the host runs with `JUDGE_ROOMS=true`, see `docs/DEPLOY.md`): open the web app, press "Start a demo auction" and follow the page `/try`, which lists the steps and the limits. If the flag is off the button falls back to the operator-key demo route and `/try` says so.
3. Bidder phone: open the join link or enter the room code in the code field (one slot per character; a pasted `GVL-` prefix is dropped), register with a name, set a ceiling on the slider and press and hold the approve button for 3 seconds. The two-tap alternative is offered below it.
4. Help: the help button on the landing, join, register, bid and receipt screens opens the hold explainer (hatched held, solid charged, hollow released) or replays the six-step guided tour (join, ceiling, hold, bid, hammer, receipt). The tour opens by itself on a first visit; `?tour=1` forces it and `?tour=0` suppresses it. Automated browsers skip it unless `?tour=1`.
5. After the hammer, the receipt shows the outcome as a settlement document with a share link, a QR code and a print layout. On the projector screen, a lot with a fundraiser goal shows a thermometer that counts only captured money. The room setup on `/try` and `/demo` has an optional "Fundraiser goal in USD" field; empty hides the thermometer, and the goal is sent as `fundraiserGoalCents` when the room is created.

Outbid, win and sold alerts sound on the bidder phone (mute toggle on the bid screen) and the projector plays a gavel sound at the hammer; browsers play sound only after a first tap on the page.

## 2. Join as a bidder

1. Open the QR link from the launcher, or `/join/<roomId>` and type the six-character code.
2. Choose "Join as bidder" and pick a ceiling (the most you may bid). The page creates a PayPal order with intent AUTHORIZE for that ceiling.
3. Approve it as a buyer:
   - PayPal sandbox buyer: sign in with a sandbox personal account. Sandbox buyer accounts are created in the PayPal developer dashboard (issue PAY-58). Credentials are never stored in this repository. Organisers hand out a test buyer at the event; never use a real account.
   - Fake buyer: in a fake-payments room the page uses the built-in fake PayPal and approves after a short pause, with no sign-in. Faults (cancel, decline, slow, error) can be simulated to test the failure screens. The hosted server never uses fake payments.
4. The ladder shows your hold moving to HELD. A hold is a promise, not a charge.

Card and guest AUTHORIZE works in our sandbox (gate G2 in `docs/GATES.md` is PASS, 2026-11-05): a wallet buyer and a guest with a sandbox card were both authorized through the JS SDK v6. A partial capture of 1.00 was accepted on the guest card authorization at age 3.5 days (early G3 probe, run 42538613566, 9 Nov); a `final_capture` and a void on a guest card authorization were not run, and the G1 capture used PayPal-account orders only.

### What judges can test on the hosted demo

The hosted server runs in sandbox mode and refuses fake payments (`packages/server/src/config.ts`). A judge therefore sees one of two things, labelled on every page:

1. Live sandbox room: needs a PayPal sandbox buyer. The sandbox buyer logins and wallet-only instructions are published in the Devpost entry and the repository's judge walkthrough, never in the source tree. Card and guest checkout may be offered: gate G2 passed (2026-11-05).
2. Simulated hold in a judge room: when a sandbox buyer is not at hand, a bidder in a judge room can test with a simulated hold (`JUDGE_SIM_HOLDS`, on by default), with no PayPal login. The room says so on screen.

For a path that needs no login and no server, open `/demo/scripted`: a recorded room that plays in your browser with no PayPal calls, labelled "Scripted demo". `/replay/:recordingId` is built but no recording is hosted yet, so it is not a judge path today.

The operator-side scripted launcher (`/api/demo/*`) uses fake payments, so it is not on the hosted server; run it locally to see the fake PayPal. The browser-only `/demo/scripted` page is hosted.

Timing. A hold older than 2 hours (`GAVEL_HOLD_MAX_AGE_MS`, 7,200,000 ms) when the settlement starts is flagged stale and a `stale_hold` row is written to the audit trail. A stale hold is still captured; the flag is a warning, not a refusal. PayPal's honor period for an authorization is unproven (gate G3), so register, bid and hammer within one sitting. A judge who registers and comes back later may see the hold flagged or voided by PayPal, in which case the bidder is dropped from the ladder as a revoked hold. Seeded demo data holds no real authorizations and is shown only as recorded events.

## 3. Bid: QR or typed entry

- QR: the big screen shows a QR code that opens `/join/<roomId>?c=<code>` on your phone. After joining, the bid screen at `/r/<roomId>/bid` has a quick-bid button, +increment buttons and a custom amount field. Bids above your ceiling are blocked.
- Typed entry: the auctioneer console at `/r/<roomId>/console` has "Manual entry" to place a bid for a registered bidder. It is recorded with source `manual`.
- Voice: the server `/audio` socket turns a spoken bid into a structured bid and asks for confirmation when the amount is ambiguous. The web console has no audio sender to that socket yet, so its microphone button is disabled and says voice is not available in this build; use manual entry. Live speech needs `VOICE_STT=groq` and `GROQ_API_KEY` on that server, and one live run of the socket is recorded (run 42575018866: 24 synthetic clips streamed with an auctioneer token to a local server with fake PayPal; both providers answered 24 of 24 and no spoken bid was accepted without a confirm; no human voice, no real room). Gate G5 stays PARTIAL, so there is no hosted voice path yet: use manual entry, the scripted demo at `/demo/scripted`, or the local fake demo.

## 4. Replay mode for voice

Replay plays a recorded bundle through the real room reducer, read only. The route shows play and pause, speed (0.5, 1, 2, 4), a scrub bar, chapter buttons (Registrations, First bid, Confirmation, Hammer, Settlement; only the ones the recording contains) and a view switch. Ladder view shows the price and the settlement ladder. Big screen view shows the public screen component. Auctioneer console view shows only the price and the settlement phase, because the live console needs a control port that a replay does not have. Recorded audio follows the replay clock when the bundle names an audio file; if it cannot load, a notice says captions only. The route reads `/recordings/<id>/events.json`, which no server or static folder serves yet, so no recording opens today and the charity gala recording is not hosted yet. The manual workflow `.github/workflows/record-judge-replay.yml` records a judge-room auction with simulated holds as a bundle (artifact `judge-replay-recording`); no bundle is hosted yet.

## 5. Expected result at the hammer

When the auctioneer hammers, check that:

1. The winner's hold is captured for the winning price only, not the ceiling. For example a $500 ceiling and a $350 winning bid captures $350.
2. Every other bidder's hold is voided. The winner's unused remainder is closed by PayPal (inferred, not observed): the settlement code reads the authorization after the capture and, if PayPal still shows an open remainder, voids it explicitly (`packages/payments/src/saga/remainder.ts`). This is tested against the fake PayPal in both modes (remainder auto-released or not). On the PayPal sandbox (gate G1, 2026-11-04) the remainder was released automatically after the final capture for a wallet buyer; an explicit void afterwards answers 422 `PREVIOUSLY_CAPTURED` and is taken as closed; the buyer balance was not read. A card-funded PayPal account also ran the capture (gate G1 run G1-20261105T123116Z, 2026-11-05). Guest card capture is untested.
3. The ladder shows HELD, then CAPTURED for the winner and VOIDED for the others, with the source of each confirmation (PayPal webhook or lookup).
4. Exactly one capture happens even if the server stops mid-settlement and resumes. If PayPal's answer is unknown the settlement stops for review rather than guessing.

The settlement logic is built and tested against the fake PayPal; the nightly sandbox run also settled one lot of three holds and recovered from one in-process crash on the real sandbox (specs R7, R8, R10, runs 42200708552 and 42317068784; see `docs/GATES.md`), but no auction has been driven through a deployed server. Gate G1 passed for two PayPal-account buyers (2026-11-04 and 2026-11-05): after a partial capture with final_capture the authorization reads CAPTURED and a void answers 422 PREVIOUSLY_CAPTURED; the release of the remainder is inferred from that, not read from a buyer balance. Gate G2 passed (2026-11-05): a wallet buyer and a guest card buyer were both authorized; a partial capture of 1.00 on the guest card authorization was accepted in the early G3 probe (9 Nov), but a `final_capture` and a void on a guest card authorization were not run. Webhook signature verification is proven on the PayPal sandbox (gate G4 PASS, 2026-11-05): six real events, including a capture and a void, each verified SUCCESS through PayPal's endpoint.

## 7. Audit trail

Open `/r/<roomId>/audit` from the launcher (it needs the auctioneer or reviewer link). The audit screen is specified to show accepted bids, rejected bids, confirmations and control actions with source, transcript and parsed amount, and to export CSV or JSON with a SHA-256 of the rows. The engine's hash-chained ledger records accepted bids (`BID_RECORDED`), each with its source (`manual`, `qr` or `voice`, as the client sent it) and an audit block that can hold the transcript, confidence and parser version. Rejected bids are not in the ledger: the server keeps them in the room log only (D-0014, D-0029), so `verify-ledger` cannot check them and the ledger export holds no `BID_REJECTED` entry. Bids that come through the voice socket carry the transcript and confidence in their audit block; QR bids carry no confidence, and manual bids record only who entered them. Settlement writes a journal of each capture and void. A ledger export can be checked without a server: `verify-ledger <ledger.jsonl>` in `packages/engine` prints the entry count and head hash, or the first bad entry, and exits non-zero on tampering.
