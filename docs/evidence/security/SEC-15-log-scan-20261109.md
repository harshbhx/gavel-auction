## Patterns

Bearer token, JWT shape (`eyJ...` with two dots), PayPal access token prefix `A21`, email address, 13 to 19 digit run, `x-admin-key` or `x-judge-key` followed by a value, `authorization` header with a Basic or Bearer value, `access_token` value, `client_secret` value, any 60 or more character run of base64 characters.

Hits inspected by hand:

- Email address: the single hit in every log is the domain `@izs.me`, an npm package author in the install output. No buyer address.
- 13 to 19 digit runs (nightly job): all 44 are the `"ts":` epoch milliseconds of the payments client log lines. None is another number.
- 60+ character runs: file paths under `/home/runner/work`, URLs, Actions cache keys and hex digests, checked by their leading 24 characters. None looked like a token. The hex digests were not checked one by one.
- The `***` marks in the nightly log are the GitHub masking of secret names in the step `env:` block (for example `PAYPAL_CLIENT_SECRET: ***`), not log output of the server.

## What this does not show

- It is not the scan the SEC-15 row asks for. The browser specs (S01 included) write only Playwright list output to the job log. The API server's own stdout and audit lines are not in these logs, so the server log after a full S01 run was not scanned.
- The nightly job logs show payments client lines (operation, status, latency, request id, PayPal debug id), not the server audit lines.
- GitHub masks the repository secret values in job logs, so a leaked secret value would have shown as `***`. The scan looked for the shapes above, not for the secret values themselves; no canary value was seeded and no negative run was made.
- Render service logs of the live API were not read (no access from this scan).
- Other nightly runs (7 Nov and earlier), the gate runs and the live runs were not scanned.

Status: SEC-15 stays OPEN. A proper closure needs a CI step that captures the server stdout of an S01 run to a file and scans it for seeded canary values and the patterns above.
