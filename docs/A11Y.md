# Accessibility (R-WEB-109 to R-WEB-118, R-QA-037)

This file records how accessibility is checked in GAVEL, what runs automatically, and what still
needs a human. It does not claim any manual result that nobody has recorded.

## Automated checks

All of these run in CI. The Playwright specs run in the `web-visual` job of
`.github/workflows/browser-specs.yml` through `npm run test:a11y -w @gavel/web`, with or without
committed screenshot baselines.

| Check                         | Where                                         | What it asserts                                                                  |
| ----------------------------- | --------------------------------------------- | -------------------------------------------------------------------------------- |
| axe-core on states (unit)     | `packages/web/test/component/a11y.test.tsx`   | No serious or critical violation on component and screen state fixtures.         |
| axe-core in a browser         | `packages/web/test/visual/a11y.spec.ts`       | Zero serious or critical violations on every route, light and projector themes.  |
| Keyboard walks                | `packages/web/test/visual/keyboard.spec.ts`   | Tab reaches controls, focus ring at least 2 px and 3:1, dialog trap and restore. |
| Reduced motion, forced colors | `packages/web/test/visual/motion.spec.ts`     | Animation duration 0s under reduce; chips and stamp keep a border when forced.   |
| Responsive                    | `packages/web/test/visual/responsive.spec.ts` | Reflow at 320 px and 200 percent zoom, screen view sizes.                        |
| Register walk by keyboard     | `packages/web/test/visual/keyboard.spec.ts`   | Name, paddle, ceiling and approve reachable with Tab, Enter and Space only.      |
| Ladder in forced colors       | `packages/web/test/visual/motion.spec.ts`     | Rungs keep icon and label; the current rung has a 2 px Highlight border.         |
| axe on the e2e stack          | `packages/e2e/specs/a11y-axe.spec.ts`         | No serious or critical violation on routes, register steps and the open dialog.  |
| Keyboard and live region      | `packages/e2e/specs/a11y-keyboard.spec.ts`    | Register form in 8 Tab presses or fewer; live region update within 200 ms.       |
| Public screen legibility      | `packages/e2e/specs/public-screen.spec.ts`    | Price text 96 px or more, base text 28 px or more, 7:1 in the projector theme.   |

Rules the specs enforce: no horizontal scroll except inside the audit table, the price text on the
public screen is large, the live region announces results, and route changes move focus to the
main heading.

## Known gaps in automation

- Scripted routes: the bid, console, public screen and receipt routes play a scripted scenario
  when the address carries `?scripted=1` (or `?transport=scenario`), with `scenario=<name>` to
  pick the script and `at=<ms>` to hold it at one moment. Without the flag every route uses the
  real connection. The e2e axe spec covers bid open, bid closed (the kill switch scenario), console,
  screen (live and sold) and receipt (held and settled) in the light and projector themes. The
  keyboard spec covers the bid button (Tab, Enter, focus stays, no trap, R-WEB-111) and the console
  hammer (Enter opens the confirm dialog, focus is trapped, Escape restores it, R-WEB-113).
  `packages/e2e/specs/happy-path.spec.ts` drives S01 bidding and settlement through the UI.
- Reached on a real seeded room (issue #2195, PR FIX-76): bid paused, bid stopped and the audit view,
  with the state set through the server's own control route and the audit view opened with the
  room's auctioneer link. `a11y-axe.spec.ts` runs axe on them in the light and projector themes.
  `a11y-keyboard.spec.ts` walks the register form past step one by keyboard (name, ceiling radios,
  Approve) and measures the radio focus ring (on the wrapping label) and the Approve ring at 2 px
  and 3:1. `a11y-emulation.spec.ts` runs a 640 by 512 zoom emulation and a forced-colours emulation
  over every route and state.
- Still not automated: the approval step itself (the PayPal popup and the return route), because it
  needs a payment return. The scripted bid is not answered by a server, so the focus check covers a
  sent bid with no reply. The 7:1 and 96 px checks on the public screen still run on a probe, not
  on real room state. A native file input is left out of the forced-colours check because the
  browser draws its button.
- Added by this change, and limited as follows. The register walk runs on a stored session that
  stands in for the invite step. The settlement ladder is checked in forced colors from a
  specimen on the gallery page at /gallery?ladder (a fixed settlement view), and its screenshot is a report
  attachment, not a compared baseline. The public screen legibility check reads computed styles
  from a probe built from the screen's own classes. The live region timing check calls the app's
  own announcer from the page.
- The e2e specs `packages/e2e/specs/a11y-axe.spec.ts`, `a11y-keyboard.spec.ts` and
  `public-screen.spec.ts` run on the e2e stack in the `e2e` jobs of
  `.github/workflows/browser-specs.yml`; their axe results are attached to the Playwright report
  as JSON.

## Manual-only checks and their automated proxies

Four checks still need a person: NVDA, VoiceOver, browser zoom at 200 percent and Windows forced
colours. This table says what runs in CI today as a proxy for each, and what could be added. A proxy
is not a pass: no row of the manual table below changes because a proxy is green, and nobody has
recorded a manual result (issue #2195 stays open for that).

| Manual check                | Automated proxy in CI today                                                                                                                                                                                                                                                                                                                                 | What it cannot show                                                                                             | Automation that could be added                                                                                                                                                                                                              |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| NVDA with Firefox           | axe-core on every web route in light and projector themes (`a11y.spec.ts`), on `/try` with the judge dialog open (merged in #2143), on the scripted e2e states (`a11y-axe.spec.ts`), and on the docs site home, a docs page, the glossary and the API reference (`docsite.yml` job `a11y`, merged in #2169). Live region timing in `a11y-keyboard.spec.ts`. | What NVDA says, in what order, and whether the wording makes sense to a listener.                               | Playwright accessibility-tree (aria snapshot) assertions for names, roles and reading order per state; a Windows runner job driving NVDA with Guidepup (feasibility not tested here). A Guidepup log is still a recorded run, not a person. |
| VoiceOver with Safari       | The e2e axe and keyboard specs run in WebKit in the e2e matrix, and the web `a11y.spec.ts` and `keyboard.spec.ts` run in a WebKit project in the `web-visual` job (an engine check; no screen reader runs).                                                                                                                                                 | VoiceOver rotor, gestures on iOS, and Safari-specific tree differences.                                         | A WebKit project for the axe and keyboard specs; a macOS runner job with Guidepup for VoiceOver (feasibility not tested here; macOS runners limit what can be automated).                                                                   |
| Browser zoom at 200 percent | `responsive.spec.ts` uses a 640 px wide viewport as 200 percent of 1280 px and checks the screen views fit; `/try` is checked for sideways scroll at 320 px and 390 px (#2143). The docs site is checked at desktop and phone width only.                                                                                                                   | Real browser zoom (text scaling, sticky headers over content, dialogs taller than the viewport).                | The 640 by 512 viewport and a 200 percent text-only emulation over every route, including the docs site, checking scroll width and clipped controls (the plan in #2195). The manual row stays until a person zooms a real browser.          |
| Windows forced colours      | `motion.spec.ts` emulates `forced-colors: active` and checks that chips and the hammer stamp keep a border and that the settlement ladder keeps its icons, labels and a 2 px Highlight border on the current rung.                                                                                                                                          | Real Windows High Contrast themes, images and SVG, and routes the spec does not open. The docs site is not run. | Run the forced-colours emulation over every route and the docs site, check that buttons, inputs and focus rings keep a border or outline, and attach screenshots to the report for a person to look at.                                     |

Audit view, bid paused and bid stopped are covered by the axe spec above; the audit view has no keyboard walk yet.
