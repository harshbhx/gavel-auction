The repository was reviewed in repeated adversarial passes: red-team rounds 1 to 13, plus separate audit passes. Every finding is a GitHub issue with a file, a line, a scenario and a suggested fix. This page shows the six findings labelled critical, the 96 labelled high grouped by theme, and the numbers behind both. It is a snapshot taken on 7 Nov 2026. Titles are quoted from the issues; nothing here is secret, because the issues are public.

## The numbers

Counted with `gh` on 7 Nov 2026 (queries at the end of the page); the open issues in "What is still open" were re-checked on 9 Nov 2026.

- 606 issues carry the `red-team` label. 589 are closed and 17 are open.
- Of those 606, 37 are batch or epic issues that track the fix work (their titles start with `FEATURE:` or `EPIC`). The other 569 are individual findings: 560 closed, 9 open.
- Severity labels on the 569 findings: 6 critical (6 closed), 96 high (93 closed), 210 medium (208 closed), 97 low (95 closed). 160 findings have no severity label (158 closed). Later rounds mostly did not set one.
- Three further label sets are separate from `red-team` and are not in the 606: `audit-r1` has 27 issues (23 closed), `audit-r2` has 33 (all closed) and `redteam-r4` has 68 (67 closed).

"Closed" means the issue is closed after a fix PR merged. The count does not separate issues closed by a code change from any closed as a duplicate or as not real, so it is not a count of code changes.

## The six critical findings

There are six critical issues but five distinct defects, because #698 and #700 report the same break. All six issues were found by reading the code in a red-team round, and each cites file and line. All six are closed. None was found by a failing test; in the web cases the existing tests passed because they only used the web package's own copy of the contract.

### 1. The web app could not talk to the server

- What was wrong: the web package kept its own copy of the wire protocol. Every frame it sent lacked the `v` field and used different names, so the server closed the socket. Every frame the server sent failed the web guard and was dropped without an error. A live <Term id="room">room</Term> could never render and no bid could be placed.
- Found: red-team round 1, on 4 Nov 2026.
- Issue: [#700](https://github.com/harshbhx/gavel-auction/issues/700), and the same break seen from the integration side in [#698](https://github.com/harshbhx/gavel-auction/issues/698).
- Fix: [PR #869](https://github.com/harshbhx/gavel-auction/pull/869) deletes the local copy and builds on `@gavel/shared`. #698 was closed by [PR #1477](https://github.com/harshbhx/gavel-auction/pull/1477).
- Regression test: `delivers frames encoded by the shared codec` and `does not send a message the shared schema rejects` in [`packages/web/test/unit/connection.test.tsx`](https://github.com/harshbhx/gavel-auction/blob/main/packages/web/test/unit/connection.test.tsx).
- Evidence: [issue #700](https://github.com/harshbhx/gavel-auction/issues/700), [issue #698](https://github.com/harshbhx/gavel-auction/issues/698), [PR #869](https://github.com/harshbhx/gavel-auction/pull/869).

### 2. Registration called hold routes that did not exist

- What was wrong: the web adapter posted to `/api/rooms/{roomId}/orders` and `/holds`, but the payments contract defines `POST /api/holds` and `POST /api/holds/{holdId}/approve`. Every registration would have hit a 404 and shown `order_failed`. The adapter also sent the bidder id and the <Term id="ceiling">ceiling</Term> from the browser, so the browser chose the <Term id="hold">hold</Term> amount.
- Found: red-team round 1, on 4 Nov 2026.
- Issue: [#699](https://github.com/harshbhx/gavel-auction/issues/699).
- Fix: [PR #1477](https://github.com/harshbhx/gavel-auction/pull/1477), merged 5 Nov 2026. The adapters call the contract routes with the shared schemas and send no bidder id.
- Regression test: `sends bodies the shared hold contract accepts and names no bidder (WEB-RT-03)` in [`packages/web/test/unit/paypalAdapter.test.ts`](https://github.com/harshbhx/gavel-auction/blob/main/packages/web/test/unit/paypalAdapter.test.ts), plus the schema tests in [`packages/shared/test/hold-contract.test.ts`](https://github.com/harshbhx/gavel-auction/blob/main/packages/shared/test/hold-contract.test.ts).
- Evidence: [issue #699](https://github.com/harshbhx/gavel-auction/issues/699), [PR #1477](https://github.com/harshbhx/gavel-auction/pull/1477).

### 3. Three frames shared one sequence number and all but one were dropped

- What was wrong: the server sends `bid_accepted`, `price` and `audit_event` with the same `seq`. The web reducer discarded any frame with `seq <= lastSeq`, so after the first one the others were lost. A bidder's own screen kept the old price and showed the wrong status. Other clients never received a live audit row. An existing test, `replay of seq [1,2,2,3] equals [1,2,3]`, encoded the wrong rule.
- Found: red-team round 2, on 4 Nov 2026.
- Issue: [#890](https://github.com/harshbhx/gavel-auction/issues/890).
- Fix: [PR #1017](https://github.com/harshbhx/gavel-auction/pull/1017). The reducer dedupes on the pair (seq, type), not on seq alone.
- Regression test: `applies bid_accepted, price and audit_event that share one seq` in [`packages/web/test/unit/roundTwoBlocking.test.ts`](https://github.com/harshbhx/gavel-auction/blob/main/packages/web/test/unit/roundTwoBlocking.test.ts). A second test in the same file, `still drops a repeat of the same type at one seq`, keeps the original protection.
- Evidence: [issue #890](https://github.com/harshbhx/gavel-auction/issues/890), [PR #1017](https://github.com/harshbhx/gavel-auction/pull/1017).

### 4. A fallback sale could be charged but never booked

- What was wrong: when the winner's <Term id="capture">capture</Term> was declined, the <Term id="saga">saga</Term> captured the runner-up. The <Term id="engine">engine</Term> still had the first bidder as winner, so `SettlementBridge.finish` threw `winner_mismatch`. The runner-up had been charged, the lot stayed in SETTLING forever, `CloseAuction` was never sent and every resume repeated the same error.
- Found: red-team round 3, on 4 Nov 2026.
- Issue: [#1060](https://github.com/harshbhx/gavel-auction/issues/1060).
- Fix: [PR #1134](https://github.com/harshbhx/gavel-auction/pull/1134), merged 4 Nov 2026. `finish()` promotes the engine through the <Term id="journal">journal</Term>'s failed bidders until the engine winner equals the charged bidder.
- Regression test: `promotes the engine to the charged runner-up, completes the lot and closes` and `resumes after a crash that happened between the promote and CompleteLot` in [`packages/payments/test/bridge/settlement-bridge.test.ts`](https://github.com/harshbhx/gavel-auction/blob/main/packages/payments/test/bridge/settlement-bridge.test.ts).
- Evidence: [issue #1060](https://github.com/harshbhx/gavel-auction/issues/1060), [PR #1134](https://github.com/harshbhx/gavel-auction/pull/1134).

### 5. One bad registration could make an auction impossible to load

- What was wrong: `Room.registerBidder` appended the registration to the log first and asked the engine afterwards. A ceiling the engine refuses (above its maximum) was therefore stored, the call threw, and every later <Term id="replay">replay</Term> hit the same throw. The room could never load again, and neither could its settlement or any other bidder's hold.
- Found: red-team round 3, on 4 Nov 2026.
- Issue: [#1061](https://github.com/harshbhx/gavel-auction/issues/1061).
- Fix: [PR #1139](https://github.com/harshbhx/gavel-auction/pull/1139), merged 4 Nov 2026. The engine registration runs before the append, and replay skips a stored registration the engine refuses so an already poisoned log still loads.
- Regression test: `does not store a registration the engine refuses, so replay still loads (SERVICE-R3-01)` and `skips an already stored registration the engine refuses instead of failing the load (SERVICE-R3-01)` in [`packages/server/test/room.test.ts`](https://github.com/harshbhx/gavel-auction/blob/main/packages/server/test/room.test.ts).
- Evidence: [issue #1061](https://github.com/harshbhx/gavel-auction/issues/1061), [PR #1139](https://github.com/harshbhx/gavel-auction/pull/1139).

## How these numbers were computed

All counts come from the GitHub issue tracker with the `gh` CLI, run on 7 Nov 2026:

```bash
R=harshbhx/gavel-auction
# totals and open counts per label
gh issue list -R $R -l red-team -s all  -L 2000 --json number --jq length   # 606
gh issue list -R $R -l red-team -s open -L 2000 --json number --jq length   # 17
for l in audit-r1 audit-r2 redteam-r4; do
  gh issue list -R $R -l $l -s all  -L 2000 --json number --jq length
  gh issue list -R $R -l $l -s open -L 2000 --json number --jq length
done
# severity, within red-team
for s in critical high medium low; do
  gh issue list -R $R -l red-team -l severity:$s -s all  -L 2000 --json number --jq length
  gh issue list -R $R -l red-team -l severity:$s -s open -L 2000 --json number --jq length
done
# every red-team issue with its title, state and dates, used for the rounds and trackers
gh issue list -R $R -l red-team -s all -L 2000 --json number,title,state,labels,createdAt,closedAt
# fix PRs: the cross-referenced events on each critical issue
gh api repos/$R/issues/<n>/timeline --paginate
gh pr view <pr> -R $R --json title,state,mergedAt,body
```

Rules applied to that data: batch issues are those whose title starts with `FEATURE:` or `EPIC`; the round is the first tag in the title (`RT`, `R2` to `R13`, and `R7P` counted in round 7); an issue counts as fixed when it is closed. The theme of each high finding was assigned by reading its title and body. Test names were read from the added lines of each fix PR's diff and checked against `main`.
