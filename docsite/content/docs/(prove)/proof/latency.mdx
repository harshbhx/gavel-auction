The live judge walkthrough (judge smoke, simulated holds) passed all 17 steps, including the hammer, on 9 Nov 2026 ([run 42584326641](https://github.com/harshbhx/gavel-auction/actions/runs/42584326641), manual dispatch, desktop profile). The earlier run after the Render redeploy ([run 42561627128](https://github.com/harshbhx/gavel-auction/actions/runs/42561627128)) passed steps 1 to 15 and 17, and step 16 (the console shows the lot as closed or sold) was fixed afterwards (issue #2208, PR #2209). The earlier smoke successes in the hosted report only loaded the landing page and are not journey evidence.

A <Term id="settlement">settlement</Term> of six holds is one truth check, one capture and five <Term id="void">voids</Term>. With three voids at a time that is two void waves. Using sandbox p95 for the capture and void calls alone gives 2 x 1235.96 + 2280.66 = 4752.58 ms before the truth check. The earlier end-to-end run (n=20) included the truth check and came in at 5591.30 ms p95, inside 6 s on that sample; the later n=49 run came in at 6927.43 ms p95, so the 6 s target is missed. The per-call p95 values of that run are order 1.23 s, authorize 1.54 s, capture 2.72 s and void 1.25 s, all above the 1 s per-call budget. Owner decision open: keep the targets, raise them with a reason, or reduce latency. Evidence: [`docs/evidence/latency`](https://github.com/harshbhx/gavel-auction/tree/main/docs/evidence/latency).

The end-to-end settlement measurement (`npm run measure:settlement -w @gavel/e2e`) runs only through the `measure-sandbox` workflow from `main`, in mode `settlement`. Run 42346811713 (20 settlements of 6 holds, 0 failed) has a redacted copy under `docs/evidence/measure/`. One target is met and one is missed (`docs/GATES.md` has the record).
