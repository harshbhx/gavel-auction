A claim without a file behind it is an opinion. This page lists the claims GAVEL makes, gives each one a status, says what it ran on, and links the file or workflow that backs it. Use the filter to show one status at a time. Hover, focus or tap a row for its limits.

## How to read the statuses

<Tabs items={['PASS', 'FAIL', 'TESTED', 'RUNNING', 'SIMULATED', 'OPEN', 'CI']}>
  <Tab value="PASS">
    A recorded run on the PayPal <Term id="sandbox">sandbox</Term> passed and the evidence is in the repository or in a named run. The limit of each pass is stated on its row. A pass on one buyer type says nothing about another.
  </Tab>
  <Tab value="FAIL">
    A recorded run failed and the stated fallback is in force. No gate reads FAIL today; <Term id="gate-g5">G5</Term> failed on its first run and now reads TESTED (synthetic clips, confirm prompt on every bid).
  </Tab>
  <Tab value="TESTED">
    A recorded run exists but does not close the question. Today that is G5: wrong accept is 0.000 on synthetic, noise-free clips, but the fixes were chosen on those same clips; a synthetic held-out noisy set measured once read above the thresholds (run 42567832671). The confirm prompt protects every voice bid: spoken bids always go through the <Term id="confirm-prompt">confirm prompt</Term>.
  </Tab>
  <Tab value="RUNNING">
    A real run is under way and has no result. Today that is <Term id="gate-g3">G3</Term>, the <Term id="honor-period">honor period</Term> and reauthorize probe on the sandbox. Day 0 was 7 November 2026 at 03:06 UTC, the checkpoints are at 3.5, 4 and 5 days, and the final reading is about 12 November at 06:17 UTC. Nothing is claimed until those readings exist.
  </Tab>
  <Tab value="SIMULATED">
    The 30 day run uses a fake clock and a model of PayPal authorization rules (`packages/payments/src/fake`). It proves our code behaves as designed if PayPal follows the model. It does not prove PayPal follows it.
  </Tab>
  <Tab value="OPEN">
    Evidence exists but the claim is not concluded, or a sign-off by a second person has not happened. The nightly sandbox report, the latency targets, the security checklist and the hosted-site walkthrough are here.
  </Tab>
  <Tab value="CI">
    A test or workflow in CI checks the property. There is no recorded run in the documentation, so the current result lives in the workflow run, not on this page.
  </Tab>
</Tabs>

<Callout type="info" title="Sandbox is not the fake">
  Sandbox means real calls to the PayPal sandbox. <Term id="fake-paypal">Fake PayPal</Term> means an in-process model in `packages/payments/src/fake`. A row says which one it ran on. Nothing here ran against live PayPal and no real money moved.
</Callout>

## Where the numbers come from

<Steps>
  <Step>
    **Gate statuses** are read from `docs/GATES.md` by `docsite/scripts/gen-repo-data.mjs` when the site is built, so the map cannot say PASS where the file says FAIL.
  </Step>
  <Step>
    **Limits** are copied from the Scope, Verdict and Evidence lines of the same file, from `docs/evidence/SIM/SIM-MULTIDAY.md` and from `docs/SECURITY-REVIEW.md`.
  </Step>
  <Step>
    **Paths** are real files on main. If a path is removed or renamed the row must be updated in the same change.
  </Step>
</Steps>

## What the map does not claim

<NotVerified title="Gaps that remain">

- G1 remainder release is inferred from the authorization state, not read from a buyer balance.
- On a guest card authorization only a 1.00 partial capture was seen (early G3 probe, 9 Nov); a `final_capture` and a void were never run.
- Speech was tested with synthetic clips; the noise in the held-out set is simulated.
- The <Term id="hammer">hammer</Term> to CAPTURED latency target (2.5 s) is missed end to end (<Term id="p95">p95</Term> 3766.67 ms, n=49, run 42563147792); the SETTLED target (6 s) is also missed (p95 6927.43 ms, n=49). The earlier n=20 run (3010.04 ms and 5591.30 ms) is a smaller sample, and the n=49 run is INCOMPLETE (1 timeout, 3 failed capture calls).
- No security checklist item has been signed off.

</NotVerified>
