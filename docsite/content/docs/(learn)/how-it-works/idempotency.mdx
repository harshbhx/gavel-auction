Pressing a lift button twice does not call two lifts. The second press carries the same intent as the first, and the system treats them as one. PayPal offers the same thing for money calls: a header named `PayPal-Request-Id`. If GAVEL sends the same id twice, PayPal does the work once and answers the repeat with the first result.

That only helps if GAVEL sends the **same** id on every try of one call, and a **different** id for a genuinely different call. This page shows how the id is made and where it is reused.

## How the id is made

The id is a fingerprint of the call, not a random number. Five parts go into a JSON array, which is hashed with SHA-256 and written in base32. The first 40 characters get the prefix `gv1-`, so every id is 44 characters long.

| Part | Example | Why it is in the fingerprint |
| --- | --- | --- |
| `auctionId` | `auc1` | A call in one auction never matches another auction |
| `op` | `capture` | An authorize and a capture of one hold get different ids |
| `holdId` | `hold-1` | Each bidder's hold has its own calls |
| `amountCents` | `35000` | A call for another amount is another call |
| `generation` | `0` | The only part that changes on purpose, see below |

Hashing a JSON array, not a joined string, means no choice of ids can produce the same input as another tuple.

## Same id on every try

<Steps>
<Step>

### Save the intent, then call

The capture saves its intent in the journal first: operation, hold, amount and request id. If the process dies after that, the intent survives.

</Step>
<Step>

### Retry inside one request

The HTTP transport retries network errors and the statuses 429, 500, 502, 503 and 504, up to four attempts of ten seconds each. The wait between attempts is random between zero and the smaller of four seconds and 250 ms times two to the power of the retry number. A `Retry-After` header is honored up to 30 seconds. Every attempt carries the same `PayPal-Request-Id`.

</Step>
<Step>

### Restart and resume

A resume finds the saved intent and sends it again, with the same id. Before it sends anything it reads the truth of the hold at PayPal: a capture that is already there is adopted and no second call is made.

</Step>
<Step>

### A new id only for a new call

If the parameters change, the id changes. A reauthorization raises the generation by one. The generation never changes on a retry or a resume.

</Step>
</Steps>

## Why the id is not the only guard

<Callout type="warn" title="An id only helps while PayPal remembers it">

If PayPal had forgotten the id, a repeated capture could run again. GAVEL therefore reads the truth before every capture and adopts what is already there. The simulation scenario S6 forgets the fake's id table at each crash point and still ends with one charge. How long the real PayPal remembers a request id has not been measured in this project.

</Callout>

If the same id is ever sent with different parameters, the fake PayPal answers with a conflict. The saga treats that as an invariant fault, a bug or a configuration problem, and stops in `FAILED_NEEDS_REVIEW` instead of trying another bidder.

## What is proven

<Tab value="Sandbox">

<Charged title="Repeat capture (R5)">

In the nightly run 42200708552 (6 Nov 2026) a second capture send with the same request id answered HTTP 200 with the same capture. One crash between capture and journal (R10) ended with one capture on the winner. See [the gates](/docs/proof/gates).

</Charged>

</Tab>
<Tab value="Fake PayPal">

The fake keeps an idempotency table keyed by operation, resource and request id. The same key with equal parameters replays the stored result; different parameters conflict. It can also forget the table on purpose (the `forget_idempotency` fault) to model a lost record.

</Tab>

<NotVerified title="Simulated, not a real host">

</NotVerified>
