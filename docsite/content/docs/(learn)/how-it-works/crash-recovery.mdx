The question a skeptical reader should ask: if the server dies at the worst moment, can the winner be charged twice, or not at all?

<CrashDiagram />

## The rule behind all three cases

On every run the <Term id="saga">saga</Term> **reads the <Term id="truth-read">truth</Term> at PayPal first**, then acts. A <Term id="capture">capture</Term> that is already there is adopted. Only when PayPal shows no capture is the saved intent sent again, with the same request id.

| Crash point | What the journal holds | What the restart does |
| --- | --- | --- |
| A: after the intent, before the call reached PayPal | Intent saved, state CAPTURING | Truth shows no capture, so the same intent is sent again with the same request id |
| B: after PayPal took the capture, before the answer was saved | The same intent, no outcome | Truth shows the capture (invoice id and amount match), so it is adopted. No second call |
| C: after `capture_ok` was saved | State CAPTURED, winner recorded | Goes on to <Term id="void">void</Term> the other <Term id="hold">holds</Term>. No capture call |

If the truth cannot be read, or PayPal does not know the hold, that is **not an answer**: the intent stays, no other candidate is tried, the unknown clock runs, and after ten minutes the <Term id="settlement">settlement</Term> goes to FAILED_NEEDS_REVIEW for a person.

## The restart, minute by minute

The first diagram shows what each crash leaves behind. This one follows the restart that comes after it. Pick a crash point, then step through what the server does.

<RecoveryTimelineDiagram />

<Steps>
<Step>

### The server calls `resume()`

`compose.ts` calls `service.resume()` once when the host boots. The service then calls it again on a timer, every 60 seconds by default.

</Step>
<Step>

### The lease may still be held

A settlement run takes a lease so that two runners never work on one auction. A process that was killed cannot give it back, so the new process is told "busy" until the lease expires. The default lifetime is 320 seconds: twice the longest a retried money call can take (four attempts of ten seconds plus the `Retry-After` waits), plus a minute. The next 60 second pass tries again. In the simulation an exception releases the lease on the way out, so those restarts do not show this wait.

</Step>
<Step>

### The journal and its audit trail are caught up

The <Term id="journal">journal</Term> is read from disk. A transition is saved first and its audit row is written after, so a crash between the two could lose the row. The journal history is the source: the run starts by appending the rows above `auditedSeq`, before any other effect.

</Step>
<Step>

### The truth is read, then the decision follows

PayPal is asked about the hold before anything is sent. Depending on where the crash was, the saved intent is sent again, a capture that is already there is adopted, or no capture call is made at all.

</Step>
<Step>

### The settlement finishes and the sweeps run

The other holds are voided, three at a time, and the settlement ends SETTLED. Every resume pass also applies <Term id="webhook">webhook</Term> events that were stored but have no result, and sweeps abandoned holds and orphan voids.

</Step>
</Steps>

## The server side

The host calls `resume()` on start and then on a timer (every 60 seconds by default). It loads every known room, continues unfinished settlements, applies stored webhook events and retries orphan voids. The <Term id="audit-trail">audit trail</Term> rows of a transition are recovered from the journal history, so a crash between a save and its audit row loses nothing.

## What has been tested

<Charged title="Injected crashes, fake PayPal">

The simulation scenario S6 kills the process at 10 boundary and idempotency-table variants and checks that every restart ends with one charge. See [the simulation](/docs/proof/simulation).

</Charged>

<NotVerified title="Not on a real host">

One in-process crash at the same place (spec R10) passed on the real <Term id="sandbox">sandbox</Term> in the nightly runs of 6 and 7 Nov 2026 (runs 42200708552 and 42317068784; redacted reports committed under `docs/evidence/nightly`). Killing a real server process on a deployed host needs a staging server that is allowed to start with the kill hook; that has not been run.

</NotVerified>
